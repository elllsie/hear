# 自然发音上线方案

## 1. 背景与目标

词汇播放需优先使用预先生成的自然发音，减少 iOS 系统 TTS 的机械感，同时保留离线缓存和异常兜底能力。

英语和德语的新自然发音均已生成并上传到 Supabase `learning-audio` Storage。由于两套完整音频会占用较多存储空间，当时确定采用“分语言启用”方案，先上线和验证德语，英语暂不在 App 中开启。

- App 已启用：`germanWordAudioVersion = "v2"`。

- 中文释义播放速度为用户统一语速的 `1.5×`，同时作用于自然中文音频和系统中文兜底。

## 3. 客户端播放策略

播放优先级统一为：

1. 检查并请求 Supabase 上的最新自然音频。
2. 下载内容必须先通过音频可解码验证。
3. 验证通过后原子写入本地 `TingHuiErAudioV3` 缓存。
4. 网络或服务器异常时，优先播放已有有效缓存。
5. 没有有效缓存时，使用 iOS `AVSpeechSynthesizer` 系统声音兜底。

为避免新版本受旧缓存影响，当前使用独立的 V4 缓存目录。每次 App 启动后，某个音频首次播放时会绕过 HTTP/CDN 旧缓存检查线上版本；同一刷新周期内使用本地缓存，避免重复请求。

中文释义清洗修复后缓存命名空间已升级为 `TingHuiErAudioV4`。CDN 穿透参数按小时轮换，App 不重启时也会在下一个刷新周期重新取得同路径的后端新音频。因此后续可直接覆盖 Supabase 原对象，无需为每次音频调整发布新 App。

## 4. 播放连续性

- 播放当前单词时，后台预加载下一条音频，优先准备中文释义。
- 中文释义在单词结束时已就绪，则立即播放。
- 预加载尚未完成或失败时，不长时间等待网络，直接使用系统声音。
- 预加载成功的音频会写入缓存，之后可直接复用。

## 5. 路径与特殊字符规则

客户端与上传脚本必须使用同一套 Storage 键规范化规则：

- 路径和文件名转小写。
- `ä/ö/ü/ß` 分别转换为 `ae/oe/ue/ss`。
- 其他非 ASCII 字符转换为下划线。
- 所有连续下划线压缩为一个。
- 移除文件名首尾的下划线和句点。

该规则已解决 `Café`、`Glace/glacé` 等特殊字符单词请求错误后回退到系统声音的问题。对 8,341 个已部署/释义音频进行了路径算法对比，修复后不一致数为 0。

## 7. 发布前验收清单

- 新安装用户能获取当前启用语言的最新自然发音。
- 旧版本覆盖安装后不会被 V2 旧缓存锁定。
- 第一次播放检查线上资源，后续播放可命中缓存。
- 断网且有缓存时播放缓存。
- 断网且无缓存时播放系统声音。
- `Café`、`Glace/glacé` 等特殊字符词能命中自然音频。
- 单词与释义之间没有明显网络等待停顿。
- 中文释义自然音频与系统兜底都使用 `1.5×` 语速补偿。

## 8. 当前结论

德语和英语自然发音均已上传并在 App 中启用。当前工作重心是补齐中文释义自然音频；在生成、上传或网络异常时，客户端仍使用系统中文声音兜底。
